# 决策日志格式规范（Decision Log / ADR）

本规范直接继承用户在 `learnbuddy` 中沉淀的最佳实践，杜绝无意义套话与繁琐流程，直击决策本质与后续避坑。

## 一、文件与组织原则

1. **就近落盘原则**：优先记录在当前研究课题 / 项目工作区根目录下的 `decisions.md`（或 `decision_log.md`）。若项目下存在 `docs/` 或 `.mycompany/memory/` 且已存在对应文件，则优先就近复用。
2. **单文件时间线 + 索引查询**：采用 Markdown 单文件递增追加。日常查阅先调 `list_decisions.ps1` 看索引目录，需要哪条再定向定位，避免把整篇长文本全量塞入 Prompt 消耗 Token。
3. **不可篡改历史，只追加修正**：一旦某项历史决策被推翻，**不要直接修改旧记录正文**。应新建一条决策，在状态栏标记 `已推翻（由 D-XXX 取代）`，形成真实的技术演进轨迹。

## 二、标准条目模板

```markdown
## D-004（2026-09-30）一句话决策标题

**决策**：明确说明项目决定**做什么**或**不做什么**。句子要果断、确凿，避免模糊不清。

**Why**：
- **背景与约束**：当时面临什么资源瓶颈、时间窗口或物理/算力限制？
- **对比权衡**：为什么选方案 A 而放弃方案 B？从工时、准确率、工程复杂度或风险控制角度说明理由。

**影响 / 必须知道的事**：
1. **反向约束（最关键）**：明确说明「**不要再把以下现象当缺陷修**」或「**后续开发严禁再踩的坑**」，防止团队或未来的自己反复推倒重来。
2. **接口与协同影响**：上下游模块需要配合调整什么参数、输入格式或假设条件？
3. **预期验证（可证伪）**：本次决策预期带来的指标提升（如耗时 ↓20%、显存占满率 <80%），事后可据此复盘。
```

## 三、触发纪律：什么时候必须记一条？

- ❌ **日常代码流水账不用记**：增加一个函数、修个拼写、改个变量名，走 git commit。
- ⭕ **遇到以下 5 类节点必须记录**：
  1. **技术路线二选一 / 方案选型**：如「放弃 3DGS 隐式渲染，改走点云 + Transformer Query」。
  2. **舍弃功能 / 裁剪边界**：如「本次竞赛/论文版本不实现全局图优化回环，仅保留高频局部里程计」。
  3. **架构反向约束**：发现某个特性故意不实现（如 LearnBuddy 舍弃认证系统），必须防止后续当作 Bug 误修。
  4. **重大踩坑与绕行方案**：如「某库在 Windows 下有 Named Pipe 限制，强制改用 TCP/Stdio 降级」。
  5. **评测口径或基线变更**：如改变 SemanticKITTI 评测序列或评估指标计算方式。
